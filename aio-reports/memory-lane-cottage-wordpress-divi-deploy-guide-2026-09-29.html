  1. Prepare your review decisions and access

    Review the 50 FAQs and send Q# edits or “ship as-is.” Choose the Google reviews and send the original source links for any replacements you want published. Confirm authorized WordPress access through your normal route. Coordinate with your site manager so two people do not change schema at once. No passwords belong in this report.

  2. Book and prepare the 30-minute Zoom session

    Book your session once the approved copy and access are ready; send FAQ edits a day or two before it. Apollo installs while you watch. Before changes begin, prepare a site backup and copies of existing code, Yoast settings, redirect rules, and Divi layouts. Prepare the location redirect review and contact corrections for the call; broader cleanup needs a separately agreed scope.

  3. Publish the visible facts in Divi

    Use Divi Text or Accordion modules to publish the assigned answers on About, Life at the Cottage, Caregiver Support Services, Resources, and Visitor Policy. Keep all answers available to visitors, including accessible accordion content. Add respite information to Life at the Cottage and link to it from navigation or the relevant care pages; a new page is not required for this package. Publish the corrected phone, inquiry hours, payment sources, tour contacts, staffing, care limits, secured outdoor setting, and fee inclusions. Keep numeric pricing unpublished under the retained “call us” default.

  4. Remove outdated people and prepare reviews

    Remove Taylor Conley and Andrew Brokenborough from team cards, Divi pop-ups, biographies, and any person records. Check pop-up templates as well as the About page. Do not replace them with guessed roles. Use only the Google reviews you have chosen; preserve exact wording, attribution, and an original source link for each approved quote. Until you supply them, do not select or publish replacement reviews. Do not install Review or AggregateRating, including for embedded Google reviews.

  5. Reconcile Yoast before injecting code

    Inspect the current rendered JSON-LD. The public homepage checked September 29 confirms the existing logo identity; keep it when merging the supplied image record. Correct the existing site description that still names Oviedo if it no longer describes the represented business. Reuse Yoast’s existing organization, website, logo, page, and breadcrumb identities. The supplied blocks describe the target combined graph: use Yoast’s supported schema filters to enrich or replace matching pieces, or retain Yoast and add only the missing properties through a page-scoped code manager. Do not paste competing full Organization, WebSite, WebPage, or breadcrumb definitions beside Yoast. Preserve existing Article markup on posts. The business and location share one identity; remove an earlier standalone location draft if one was ever installed.

  6. Validate the final code before installation

    Parse every final payload as JSON. Use Schema.org Validator for the complete graph and Google Rich Results Test only for supported features. FAQPage must exactly match the approved visible answers; no Google FAQ rich result is promised. No eligible rich-result items does not mean the schema failed.

  7. Install approved, page-scoped JSON-LD

    Use the site’s existing code manager if it can target pages. Otherwise Apollo may install Header Footer Code Manager during the authorized deploy session. Choose an HTML snippet in the header, wrap only the downloaded JSON-LD in a script of type application/ld+json, and set display rules to the named page. Only the reconciled sitewide identity belongs on all pages. Do not put every FAQ or service block into Divi Theme Options → Integration, which is global. Do not paste package metadata or this guide into a code field. If using Divi Code modules instead, target only the matching page and inspect rendered output after saving.

  8. Verify the installed pages

    After saving, clear SiteGround Optimizer and Divi caches, inspect rendered desktop and mobile pages, compare the actual Q&A text to markup, check there is one consistent business identity, and confirm no outdated phone or removed people remain. Test every changed canonical URL and redirect.

  9. Record proof and retain rollback

    Save the tested page addresses, timestamps, final JSON-LD, validator results, screenshots, and the exact changes made. Confirm the canonical pages are indexable and submit them for re-crawl in Search Console when authorized access is available. If output conflicts or page layout breaks, disable the new snippets, restore the saved Yoast/Divi settings and redirect rules, clear caches, and recheck the original pages. Never delete existing working schema without a restoration copy.

  10. Schedule the single follow-up

    Freeze the supplied baseline as the dated pre-deployment research record; add deployment date and verification in a separate receipt without rewriting the capture. Run one Pulse check 30 days after execution using the same tracked project, fixed questions, platform set, and comparable time window. Keep the September 17 one-run capture separate. If the gap between research and deployment makes a new baseline necessary, preserve this file and capture a new dated baseline rather than overwriting it.
